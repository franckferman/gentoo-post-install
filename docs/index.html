Why

Gentoo deserves its own post-install

⚙️ Portage configuration

Auto MAKEOPTS (cores capped by RAM), COMMON_FLAGS, CPU_FLAGS_X86 via cpuid2cpuflags, sane FEATURES.

📦 Binary packages

Opt-in official Gentoo binhost with signature trust - turn a source distro into fast installs when you want them.

🔁 World maintenance

Sync, news, @world update, preserved-rebuild and depclean - the routine, done right.

🛡️ Hardening

sysctl drop-in, default-deny firewall (nftables/iptables/ufw, SSH-safe), hardened OpenSSH, audit, fail2ban, AppArmor.

🖥️ Desktop & shell

VIDEO_CARDS autodetect, Xorg/Wayland, PipeWire, NetworkManager, zsh + powerlevel10k, Nerd Fonts.

↩️ Reversible

Dry-run, idempotent steps, automatic make.conf backup, marked drop-ins, and a one-command --rollback.

Quick start

Get going in three lines

⚠️ This changes system config. Read the script, run --dry-run first, and review Portage news.

# Download
curl -O https://raw.githubusercontent.com/franckferman/gentoo-post-install/stable/gentoo-post-install.sh
chmod +x gentoo-post-install.sh

# Preview - no changes made
sudo ./gentoo-post-install.sh --dry-run

# Desktop workstation, non-interactive, with binhost
sudo ./gentoo-post-install.sh --profile desktop --binhost -y

Fresh install → usable

Bare Gentoo to a working desktop

No Flatpak by default: apps come from Portage and overlays. Obsidian comes from the r7l overlay (auto-enabled); Discord and Signal are in the main Gentoo tree; Steam is native via steam-overlay (needs a multilib profile).

# KDE desktop with apps, from a fresh install
sudo ./gentoo-post-install.sh --profile desktop --de kde --dm sddm \
     --apps firefox,vlc,obsidian,keepassxc

# Tiling Wayland + a ready-made app set
sudo ./gentoo-post-install.sh --de sway --apps-profile daily

# Gaming box: native Steam + Discord
sudo ./gentoo-post-install.sh --apps-profile gaming --steam

# Discover what's available
./gentoo-post-install.sh --list-apps
./gentoo-post-install.sh --list-overlays
Hardening

Safe by construction

🧱 Firewall, no lockout

Default-deny inbound with an SSH allow rule by default. nftables rulesets are validated with nft -c before apply; iptables adds accept rules before switching the policy to DROP.

🔑 SSH

Modern KEX/ciphers/MACs, MaxAuthTries, agent/TCP forwarding off. The drop-in is validated with sshd -t and only restarted after you confirm.

🧮 sysctl

rp_filter, redirects off, syncookies, kptr_restrict, dmesg_restrict, Yama ptrace scope, protected symlinks/hardlinks/fifos.

🛰️ Detection & MAC

auditd + system logging, fail2ban sshd jail, optional USBGuard and AppArmor with the kernel LSM cmdline spelled out.

Undo

One command to revert

Every managed file carries a gentoo-post-install marker and make.conf is backed up before editing.

sudo ./gentoo-post-install.sh --rollback

Restores make.conf and removes the managed drop-ins (CPU flags, USE baseline, sysctl, binhost, fail2ban jail, SSH drop-in) and the sudoers grants it created. It deliberately does not uninstall packages, disable services, delete accounts, or touch /etc/nftables.conf.

Requirements

What you need

  • A Gentoo system with Portage (emerge) available
  • Root via sudo/doas, or --allow-root
  • Network access for sync and package installs
  • Works on both OpenRC and systemd - detected automatically
FAQ

Questions, answered

Does it work on both OpenRC and systemd?

Yes - the init system is detected and every service action is abstracted, so the same run drives rc-update/rc-service or systemctl automatically.

Will it break my system?

It is dry-run-first and idempotent: preview everything with --dry-run, make.conf is backed up before editing, managed files are marked, and a single --rollback reverts them. Nothing destructive runs without opt-in.

Flatpak or native?

Native by default. Apps come from Portage and overlays (via eselect-repository); Steam is native through the steam-overlay. Flatpak is only an optional escape hatch.

Can I choose and harden my own kernel?

Yes: pick the source (bin/dist/source/vanilla) and a config profile (standard/hardened/minimal/performance). Hardened uses the Gentoo KSPP toggle; lockdown and a KSPP cmdline are opt-in. A custom config can fail to boot, so the previous kernel is always kept.

How are passwords handled?

Always read from a masked prompt and applied via chpasswd on stdin - never in argv or a file. Every sudoers drop-in is validated with visudo -c, and --disable-root refuses to run without a non-root admin.

Is it tested?

Static analysis (ShellCheck), a 72-check unit suite (mocked commands), a 30-check fake-root integration suite (real writes to a temp tree), a 9-check dry-run smoke matrix, and a dry-run of every profile all pass in CI - plus an optional isolated QEMU boot-test. Real end-to-end execution on live hardware is yours to validate - start with --dry-run.
